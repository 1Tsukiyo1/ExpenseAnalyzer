# Архитектура и функции

## Архитектура решения

В решении два проекта:

- ExpenseAnalytics.Core — библиотека с моделями расходов, правилами проверки, отбором и формированием отчётов. Код библиотеки не обращается к консоли, файлам или глобальному состоянию.
- ExpenseAnalyticsConsoleApp — консольное приложение. Оно показывает меню, читает и разбирает ввод, хранит текущий список расходов, вызывает функции Core и выводит результаты.

Единственное направление зависимости — `ExpenseAnalytics.ConsoleApp` → `ExpenseAnalytics.Core`. Благодаря этому библиотеку можно повторно использовать из приложения с другим интерфейсом, не меняя вычислительную логику.

Модель `Expense` — record, но это не означает глубокую неизменяемость всего приложения. Методы обработки не изменяют переданные им коллекции; `AppendImmutable` создаёт новый список. При этом возвращаемый список остаётся обычным изменяемым `List<T>`, а элементы не копируются глубоко.

## Модели

- `Expense` — расход: Id, дата, категория, описание и сумма.
- `ExpenseInput` — введённые категория, описание и сумма, передаваемые правилам проверки.
- `ExpenseCriteria` — необязательные критерии отбора.
- `CategoryTotal` — сумма расходов по категории.
- `DailyTotal` — сумма за день и накопленный итог.
- `ExpenseReport` — сводные показатели, категории, крупнейшие расходы и дневные итоги.

## Публичные функции библиотеки

### `AllOf<T>`

```csharp
public static Predicate<T> AllOf<T>(
    IReadOnlyList<Predicate<T>> predicates)
```

- Назначение: объединяет предикаты по логике AND.
- Входные данные и ограничения: список предикатов; `null` не допускается.
- Результат: новый `Predicate<T>`.
- Граничные случаи: пустой список даёт предикат, возвращающий `true` для любого значения.
- Чистота и предположения: создание результата не вызывает переданные предикаты. При создании копируется список делегатов, но не состояние, захваченное ими. Предполагаются чистые предикаты и стабильность их зависимостей.
- Поведение делегатов: при проверке вызываются по порядку; каждый вызывается не более одного раза на проверяемое значение; после первого `false` проверка прекращается.
- Почему выделена отдельная функция: позволяет собирать составные условия отбора из отдельных правил без дублирования логики AND.
- Почему выбран этот способ реализации: копия массива фиксирует состав и порядок условий, а цикл обеспечивает короткое замыкание после первого `false`.
- Где используется: `SelectExpenses`.

### `ValidateAll<T>`

```csharp
public static List<string> ValidateAll<T>(
    T value,
    IReadOnlyList<Func<T, string?>> rules)
```

- Назначение: запускает все правила проверки значения и собирает сообщения об ошибках.
- Входные данные и ограничения: проверяемое значение и список правил; `null` для списка не допускается.
- Результат: список сообщений об ошибках.
- Граничные случаи: для пустого списка правил возвращается пустой список ошибок.
- Чистота и предположения: сама функция не выполняет ввод-вывод и не меняет входные данные. Для сохранения чистоты правила должны быть чистыми; исключения, выброшенные правилом, не перехватываются.
- Поведение делегатов: каждое правило вызывается ровно один раз в порядке списка. Функция не прекращает проверку после первой ошибки. `null` от правила означает успешную проверку.
- Почему выделена отдельная функция: позволяет добавлять правила проверки без отдельного повторения цикла обработки ошибок.
- Почему выбран этот способ реализации: полный проход даёт пользователю все обнаруженные ошибки за одну попытку.
- Где используется: консольный `AddExpense` применяет функцию к категории, описанию и сумме после разбора даты и суммы.

### `MapAccum<T, TState, TResult>`

```csharp
public static (TState FinalState, List<TResult> Items)
    MapAccum<T, TState, TResult>(
        IEnumerable<T> source,
        TState initialState,
        Func<TState, T, (TState NextState, TResult Item)> step)
```

- Назначение: проходит последовательность, передавая состояние от элемента к элементу и формируя результат для каждого элемента.
- Входные данные и ограничения: источник, начальное состояние и функция шага; `null` для источника или шага не допускается.
- Результат: итоговое состояние и список результатов в порядке входных элементов.
- Граничные случаи: для пустого источника возвращаются исходное состояние и пустой список.
- Чистота и предположения: функция не использует внешний изменяемый аккумулятор. Для функционального стиля шаг должен возвращать новое состояние, а не изменять переданное состояние.
- Поведение делегатов: источник перечисляется один раз; `step` вызывается ровно один раз на элемент и в порядке перечисления.
- Почему выделена отдельная функция: накапливаемый расчёт отделён от источника данных и может использоваться с разными типами состояния и результата.
- Почему выбран этот способ реализации: явная передача состояния делает зависимость каждого шага от предыдущего понятной. В отличие от изменения внешней переменной внутри `Select`, здесь нет побочного эффекта в LINQ-лямбде.
- Где используется: `CreateReport` рассчитывает накопленные суммы по предварительно сгруппированным и отсортированным дням.

### `AppendImmutable<T>`

```csharp
public static List<T> AppendImmutable<T>(
    IReadOnlyList<T> source,
    T item)
```

- Назначение: возвращает новый список, содержащий исходные элементы и добавленный в конец элемент.
- Входные данные и ограничения: исходный список и добавляемый элемент; `null` для списка не допускается.
- Результат: новый `List<T>`.
- Граничные случаи: для пустого списка возвращается список из одного элемента.
- Чистота и предположения: исходный список не изменяется. Элементы не копируются глубоко; возвращаемый список сам по себе изменяемый.
- Почему выделена отдельная функция: консольное приложение может заменить ссылку на список, не изменяя прежнюю коллекцию.
- Почему выбран этот способ реализации: явное копирование сохраняет порядок элементов и отделяет новый список от исходного.
- Где используется: консольный `AddExpense`.

### `ValidateCategory`

```csharp
public static string? ValidateCategory(ExpenseInput input)
```

- Назначение: проверяет, что категория не `null`, не пустая и не состоит только из пробельных символов.
- Входные данные и ограничения: `ExpenseInput`; предполагается, что передан корректный объект.
- Результат: текст ошибки или `null`, если проверка пройдена.
- Граничные случаи: пустая строка и строка из пробелов считаются ошибкой.
- Чистота и предположения: чистая функция, не меняет входные данные и не выполняет ввод-вывод.
- Почему выделена отдельная функция: правило категории можно повторно использовать и включать в общий список проверок.
- Почему выбран этот способ реализации: `string.IsNullOrWhiteSpace` одновременно обрабатывает пустую строку и пробельные символы.
- Где используется: как правило `ValidateAll` при добавлении расхода.

### `ValidateAmount`

```csharp
public static string? ValidateAmount(ExpenseInput input)
```

- Назначение: проверяет, что сумма расхода больше нуля.
- Входные данные и ограничения: `ExpenseInput`; предполагается, что сумма уже разобрана в `decimal`.

- Граничные случаи: ноль и отрицательное значение не допускаются.
- Чистота и предположения: чистая функция, не меняет входные данные.

- Почему выбран этот способ реализации: сравнение с нулём выполняется после успешного преобразования текста в `decimal`.
- Где используется: как правило `ValidateAll` при добавлении расхода.

### `SelectExpenses`

```csharp
public static List<Expense> SelectExpenses(
    IReadOnlyList<Expense> expenses,
    ExpenseCriteria criteria)
```

- Назначение: отбирает расходы по заданным критериям.
- Входные данные и ограничения: список расходов и объект критериев; `null` не допускается. Если заданы обе даты, начальная дата должна быть не позже конечной.
- Результат: новый список совпавших расходов; исходный список не сортируется и не изменяется.
- Граничные случаи: без критериев возвращаются все расходы; границы дат и минимальной суммы включительны; обратный диапазон дат вызывает `ArgumentException`.
- Чистота и предположения: функция не выполняет ввод-вывод и не меняет входные данные.
- Почему выделена отдельная функция: логика отбора доступна независимо от консольного интерфейса.
- Почему выбран этот способ реализации: каждое заданное условие оформляется отдельным предикатом, `AllOf` объединяет их, а LINQ `Where` применяет общий предикат через лямбда-адаптер.
- Сравнение категорий: крайние пробелы удаляются через `Trim`; сравнение выполняется без учёта регистра с `OrdinalIgnoreCase`.
- Где используется: консольные команды отбора и формирования отчёта.

### `SortExpenses`

```csharp
public static List<Expense> SortExpenses(
    IEnumerable<Expense> expenses)
```

- Назначение: упорядочивает расходы сначала по дате, затем по Id.
- Входные данные и ограничения: перечисление расходов.
- Результат: новый список, отсортированный по возрастанию даты и Id.
- Граничные случаи: пустой источник даёт пустой список.
- Чистота и предположения: входное перечисление не изменяется; при перечислении источника предполагается отсутствие побочных эффектов.
- Почему выделена отдельная функция: один порядок вывода используется и при показе списка, и при просмотре результатов отбора.
- Почему выбран этот способ реализации: LINQ `OrderBy` и `ThenBy` явно выражают ключи сортировки.
- Где используется: консольные команды показа всех расходов и результатов отбора.

### `CreateReport`

```csharp
public static ExpenseReport CreateReport(
    IEnumerable<Expense> expenses)
```

- Назначение: формирует сводный отчёт по переданным расходам.
- Входные данные и ограничения: перечисление расходов; `null` не допускается.
- Результат: количество, общая сумма, средняя сумма, суммы по категориям, до трёх крупнейших расходов и дневные суммы с накопительным итогом.
- Граничные случаи: для пустого результата количество и сумма равны 0, среднее равно `null`, остальные списки пусты.
- Чистота и предположения: функция не меняет входные данные и не выполняет ввод-вывод. Для однократной материализации используется `ToList`.
- Почему выделена отдельная функция: отчётная логика отделена от консольного форматирования и может повторно использоваться.
- Почему выбран этот способ реализации: LINQ применяется для сумм, группировок, сортировки и выбора топ-3; `MapAccum` — для последовательного расчёта накопленного итога.
- Группировка категорий: ключ категории нормализуется через `Trim`, сравнение групп выполняется с `StringComparer.OrdinalIgnoreCase`.
- Где используется: консольная команда формирования отчёта.

## Ключевые решения

### Почему для отбора используются `Where` и `AllOf`

`AllOf` формирует один предикат из набора отдельных условий: дат, категории и минимальной суммы. Это позволяет добавлять критерии независимо друг от друга и применять их совместно по логике AND. LINQ `Where` фильтрует последовательность этим предикатом.

`AllOf` возвращает `Predicate<T>`, тогда как `Where` принимает `Func<T, bool>`. Поэтому используется адаптер:

```csharp
expenses.Where(expense => selection(expense))
```

### Почему проверяются все ошибки

При добавлении пользователю полезнее сразу увидеть все ошибки, а не исправлять их по одной. `ValidateAll` поэтому проходит по всем правилам и собирает каждое сообщение. Ошибки разбора даты и суммы возникают раньше — при преобразовании текста — и обрабатываются консольным приложением отдельно.

### Почему `MapAccum`, а не изменение внешней переменной в `Select`

Изменение внешнего накопителя внутри `Select` превращает LINQ-выражение в операцию с побочным эффектом. Результат может зависеть от количества и порядка перечислений. `MapAccum` явно передаёт состояние между шагами, перечисляет источник один раз и возвращает результаты в порядке входных данных.

### Что даёт копирование списка при добавлении

`AppendImmutable` копирует ссылки на существующие элементы в новый список и добавляет новый элемент в конец. Исходный список остаётся без изменений, поэтому консольная оболочка может заменить своё состояние новым списком.

Это не глубокая копия: объекты-элементы не клонируются. Новый `List<T>` также можно изменять. Цена операции — копирование всех элементов, то есть O(n) времени и дополнительной памяти.

### Где достаточно LINQ, а где нужна собственная функция

LINQ используется для стандартных операций над последовательностями: `Where`, `OrderBy`, `ThenBy`, `GroupBy`, `Sum`, `Take`, `Select`, `ToList`. Собственные функции оправданы там, где задание задаёт отдельный контракт: объединение предикатов, сбор всех ошибок, передача накопительного состояния и добавление в новый список.

## Конвейеры обработки

### Добавление расхода

1. ConsoleApp: `AddExpense` запрашивает дату, категорию, описание и сумму.
2. ConsoleApp: дата разбирается через `DateOnly.TryParseExact`, сумма — через `decimal.TryParse`. Ошибки формата собираются до проверки бизнес-правил.
3. Core: если разбор прошёл, `ValidateAll` вызывает `ValidateCategory`, `ValidateDescription` и `ValidateAmount`.
4. ConsoleApp: при ошибках состояние списка не меняется. При успехе приложение назначает Id: максимальный существующий Id + 1, либо 1 для пустого списка.
5. Core: `AppendImmutable` создаёт новый список.
6. ConsoleApp: новая ссылка присваивается переменной `expenses`.

### Отбор и отчёт

1. ConsoleApp: `ReadCriteria` собирает необязательные критерии; `SelectWithRetry` повторяет ввод, если начальная дата позже конечной.
2. Core: `SelectExpenses` создаёт предикаты критериев и объединяет их через `AllOf`.
3. Core: `Where` применяет составное условие и возвращает новый список.
4. ConsoleApp: для простого просмотра вызывает `SortExpenses`; для отчёта вызывает `CreateReport`.
5. Core: `CreateReport` вычисляет метрики, группирует категории и дни через LINQ, выбирает крупнейшие расходы и вычисляет дневной накопительный итог через `MapAccum`.
6. ConsoleApp: `PrintExpenses` или `PrintReport` форматирует и выводит результат.
